# WebAudit 不正アクセス分析報告書の出力機能改善

## 1. 目的

`mikoto2000/webaudit` のレポート出力機能を改善し、アクセスログを用いた不正アクセス調査において、調査結果を第三者に提出できる品質の報告書を生成できるようにしてください。

今回想定する調査業務は、アクセスログから不正アクセスの疑いがあるリクエストを抽出し、その根拠、傾向、攻撃成立の可能性、追加調査の必要性を報告するものです。

アクセスログだけからシステムへの侵入や被害の発生を断定することは目的としません。

以下の4点を重視してください。

- 網羅性：何を調査し、何を調査できなかったかが分かること。
- 再現性：同じログと解析条件から同等の結果を得られること。
- 追跡可能性：報告書の指摘から根拠となる元ログまでたどれること。
- 判断の妥当性：観測事実、分析による推定、未確認事項が区別されていること。

## 2. 基本方針

- まず既存のソースコード、テスト、設計文書、出力仕様を確認すること。
- 既存の解析機能、検出ルール、事案モデル、成否判定、GeoIP、CrowdSec Hub / Aura 互換検出を可能な限り再利用すること。
- 既存機能で取得できる情報を重複実装しないこと。
- 報告書の記載に必要な情報が取得できない場合は、必要性を評価した上で解析機能を拡張すること。
- 取得できない情報を推測や固定値によって補完しないこと。
- オフラインで完結する CLI という既存の設計思想を維持すること。
- 大規模ログをストリーミング処理する既存の設計を維持すること。
- 既存の CLI、HTML、JSON、CSV 出力との後方互換性を考慮すること。
- 外部の LLM や API を必要とせず、決定的な処理によって報告書を生成すること。
- 今回はバッチ解析における報告書生成を対象とし、リアルタイム監視機能の大幅な変更は行わないこと。

## 3. 報告書の構成

報告書は以下の章構成としてください。

### 第1章 調査概要

報告書の読者が、この章だけで調査範囲と主要な結果を把握できるようにしてください。

#### 調査基本情報

- 報告書名
- 対象システム名
- 調査背景
- 調査目的
- 調査対象期間
- 解析実施日時
- 調査実施者
- WebAudit のバージョン
- 解析状態（完了・部分解析・失敗）

システム名、調査背景、調査実施者など、ログから取得できない情報については利用者が任意に指定できるようにしてください。未指定の場合は未指定であることを明示してください。

#### 調査結果サマリー

- 入力ログファイル数
- 総ログ行数
- 解析成功行数
- 解析失敗行数
- 総リクエスト数
- ユニークアクセス元 IP 数
- 不審リクエスト数
- 不審リクエストの割合
- 不審アクセス元 IP 数
- 検出数
- 検出事案数
- 重要度別の検出事案数
- 攻撃種別ごとの検出件数
- 攻撃成否判定別の事案数
- 優先的な追加調査が必要な事案数
- 解析上の主要な警告

リクエスト数、検出数、事案数は明確に区別してください。

集計が不完全な場合は、正確な件数であるか、下限値であるか、推定値であるかを明示してください。

- アクセス元 IP アドレスの取得方法
- 利用可能なログ項目
- 利用できないログ項目

#### 入力ファイル一覧

- 圧縮形式

- 解析失敗行数
- 除外行数
- 解析状態
- 打ち切りの有無
- 警告・エラー

#### 調査対象外

- レスポンスボディ
- 認証ログ
- アプリケーションログ
- データベースログ

- その他、今回の入力から取得できない情報

ルールが無効化されている場合や、必要なログ項目が不足している場合も識別できるようにしてください。

### 第4章 判定基準

以下の評価軸を独立して扱ってください。

#### 重要度（Severity）

想定される影響や追加調査の優先度を示します。

| 重要度 | 基準 |
|---|---|
| Critical | 重大な影響を示す強い証拠があり、即時対応を要する |
| High | 重大な攻撃や攻撃成立が疑われ、優先的な調査を要する |
| Medium | 攻撃試行や不審な活動が疑われる |
| Low | 探索行為や比較的弱い異常兆候 |
| Informational | 参考情報 |

#### 検出確度（Detection Confidence）

観測されたアクセスが攻撃試行や不審な活動であることを示す根拠の強さを表します。

| 検出確度 | 基準 |
|---|---|
| High | 攻撃を示す明確な特徴がある |
| Medium | 不審な特徴があるが正常アクセスの可能性もある |
| Low | 判断根拠が限定的である |
| Unknown | 評価できない |

#### 攻撃成否（Outcome）

攻撃試行の検出と、攻撃成立の評価は分離してください。

- 成功確認
- 成功の疑い
- 成否不明
- 失敗の疑い
- 失敗確認

既存の outcome モデルとの整合性を維持してください。

アクセスログのみでは確認できない成功・失敗を確定扱いしないこと。

#### 攻撃成否の確信度

攻撃成否の推定に用いた証拠の強さを、検出確度とは別に扱ってください。

既存スコアを統計的に校正された確率として表現しないでください。

既存のスコア、重要度、確信度と上記の評価軸の対応関係を調査し、意味の異なる値を安易に変換しないこと。評価に必要な情報が不足する場合は評価不能として扱ってください。

- レスポンスサイズの統計
- リクエスト処理時間の統計（取得可能な場合）

#### 時系列統計

- 日別リクエスト数

- 不審リクエスト数の推移

- 5xx レスポンス数の推移

対象期間に応じて適切な集計粒度を選択してください。

#### 地理・ネットワーク統計

GeoIP / ASN データベースが利用可能な場合、以下を記載してください。

- 国別リクエスト数
- 国別不審リクエスト数
- ASN 別リクエスト数
- ASN 別不審リクエスト数

- 国・ASN 別のユニーク IP 数
- 国・ASN 情報の取得状況
- 使用した GeoIP データベースの情報

国や ASN だけを理由に悪性と判断しないでください。

#### グラフ

HTML レポートには以下のグラフを適切に配置してください。

- リクエスト数の時系列推移
- 不審リクエスト数の時系列推移
- HTTP ステータスコード別件数
- HTTP メソッド別件数
- アクセス元 IP 別件数の上位ランキング
- URI パス別件数の上位ランキング
- 攻撃種別ごとの検出件数
- 重要度別事案数
- 攻撃成否判定別事案数
- 国別・ASN 別件数（利用可能な場合）

グラフは外部 CDN や外部リソースに依存せず、オフラインで表示できること。

色だけに依存した情報伝達を避け、凡例、ラベル、件数を併記してください。

- その他、既存ルールで評価している観点

未実装の調査観点については未対応と記載してください。この一覧を満たすためだけに新しい検出機能を無条件に実装する必要はありません。

#### 調査観点別一覧

以下の情報を表形式で出力してください。

- 調査観点 ID
- 調査観点名

- 検出あり

- 部分評価
- 評価不能
- 未対応
- 未実施

検出ありと部分評価が同時に成立する場合があるため、内部データモデルでは評価の完全性と検出の有無を独立した属性として扱ってください。

エンジン間で事案の統合ができない場合は、その制約を明示した上で別集計としてください。

- 管理画面のアクセス制限確認
- WAF ルールの見直し
- レートリミットの検討
- ログ記録項目の見直し
- ログ保存期間の見直し
- 継続監視

検出結果と関係のない対策を無条件に大量出力しないでください。

追加調査によって攻撃成否を確認する対応と、将来の攻撃を防止する対策を区別してください。

## 4. 不審リクエスト全件出力

代表証跡とは別に、検出された不審リクエストの全件を機械処理可能な形式で出力できるようにしてください。

少なくとも以下の項目を持たせてください。

| 項目名 | 内容 |
|---|---|
| request_id | リクエスト識別子 |
| finding_ids | 関連事案 ID |
| detection_ids | 関連検出 ID |
| timestamp | アクセス日時 |
| source_ip | アクセス元 IP |
| country_code | 国コード |
| asn | ASN |
| as_organization | ASN 組織名 |
| host | アクセス先ホスト |
| method | HTTP メソッド |
| protocol | HTTP プロトコル |
| request_uri | 元のリクエスト URI |
| normalized_uri | 正規化後の URI |
| status_code | HTTP ステータスコード |
| response_bytes | レスポンスサイズ |
| request_duration | リクエスト処理時間 |
| referer | Referer |
| user_agent | User-Agent |
| attack_categories | 攻撃種別 |
| rule_ids | 検出ルール ID |
| detection_engines | 検出エンジン |
| severity | 重要度 |
| detection_confidence | 検出確度 |
| detection_reason | 検出根拠 |
| source_file_id | 元ログファイル識別子 |
| source_file | 元ログファイル名 |
| source_line | 元ログ行番号 |

攻撃成否は原則として事案に対する評価とし、事案全体の成否を個々のリクエストに無条件で転記しないでください。

単一のリクエストが複数のルールに一致しても、不審リクエスト一覧では原則として1件として扱ってください。

一方、内容が同一でも元ログ上の異なる観測は別のリクエストとして扱ってください。

### 全件出力の設計上の注意事項

現行の証跡保持上限を単純に撤廃することは禁止します。

大規模ログを処理する際にもメモリ使用量が無制限に増加しないよう、以下の方式を比較検討してください。

- ストリーミング出力
- 一時ファイルへのスプール
- ディスクベースの中間インデックス
- 解析終了後の元ログ再走査
- 上記の組み合わせ

シグネチャ検出だけでなく、解析終了時に成立する統計分析や時間窓分析、相関分析に関連するリクエストも扱えること。

ただし、相関事案に関連付けられたという理由だけで、正常なリクエストまで不審リクエストと分類しないこと。直接検出されたリクエストと、分析上の関連証跡を区別してください。

再走査する場合は、初回解析後に入力ログが変更されていないことを検証してください。

全件出力が保証できない場合は、不完全であることとその理由を明示してください。

## 5. データモデル

以下の概念を明確に分離してください。

### Request

元のアクセスログにおける1件のリクエスト。

### Detection

リクエストまたは複数のリクエストを対象とする検出ルール・分析条件の成立結果。

### Finding / Incident

関連する検出結果をまとめた分析事案。

### Investigation Recommendation

検出事案に対する追加調査・推奨対応。

### Coverage

調査観点ごとの実施状況、評価の完全性、検出結果、制約。

### Report

解析条件、統計、検出事案、調査観点別結果、総合評価をまとめた報告書。

これらの概念を既存のデータモデルと照合し、必要な部分のみ拡張してください。

Request、Detection、Finding の件数を混同しないこと。

各データ間を安定した識別子で関連付け、報告書から元ログまで追跡できるようにしてください。

HTML、JSON、CSV でそれぞれ別個の集計・判定を実装せず、共通の解析結果モデルから生成してください。

提出用の報告書本体と、詳細分析・再現性確認用の別紙を出力してください。

```text
report/

├── report.json
├── manifest.json
├── log-inventory.csv
├── analysis-rules.csv
├── analysis-coverage.csv

├── detections.csv
├── suspicious-requests.csv

├── recommendations.csv
├── statistics/

│   ├── status-summary.csv
│   ├── method-summary.csv
│   ├── ip-summary.csv
```

各ファイルの必要性と既存出力との重複を検討し、合理的な構成に調整して構いません。

既存の単一ファイル出力に加え、このような報告書一式を明示的に出力するモードを検討してください。

利用者が報告書一式を必要としていない場合に、不要な大量ファイルを生成しないこと。

### manifest.json

- 出力スキーマバージョン
- WebAudit バージョン

- 解析開始・終了日時
- 実行時オプション

- 解析上限
- 解析の完全性
- 警告・エラー
- 生成した成果物一覧
- 各成果物のハッシュ

秘密情報を含むオプションや設定値は適切にマスキングしてください。

## 7. HTML レポートの表示要件

HTML レポートは実務上の読みやすさを重視してください。

- 日本語・英語に対応する。
- 既存の `--lang` の仕様を可能な限り維持する。
- 目次を設ける。
- 調査結果サマリーを先頭に配置する。
- 調査観点一覧から関連事案へ移動できる。
- 事案一覧から詳細分析へ移動できる。
- 詳細分析から一覧へ戻れる。
- 関連する事案・検出ルールを参照できる。
- 表には項目名、単位、件数を明示する。
- 長い URI やログ文字列によってレイアウトが崩れない。
- 不審リクエスト全件を HTML 本文へ埋め込むことは必須としない。
- 大規模な調査結果でもブラウザーが過度な負荷を受けない。
- 印刷時に読みやすいレイアウトを用意する。
- 外部 CDN・外部 JavaScript・外部画像に依存しない。
- 色弱の利用者にも判別できるようにする。
- 重要度や判定結果を色だけで表現しない。

既存の HTML レポートの安全性を維持してください。

## 8. セキュリティ要件

アクセスログは攻撃者が制御可能な文字列を含む、信頼できない入力として扱ってください。

- HTML インジェクション対策
- XSS 対策
- SVG やグラフへの文字列埋め込み時の安全性
- CSV インジェクション対策
- JSON の安全なシリアライズ
- 制御文字の安全な取り扱い
- ターミナルエスケープシーケンス対策
- パストラバーサル対策
- 一時ファイルの安全な作成・削除
- 出力ファイルの安全な作成
- 既存ファイルの意図しない上書き防止
- 認証トークン・Cookie・個人情報等の取り扱い
- 資源枯渇対策

既存の証跡保持・入力サイズ・解析キー数などの上限を尊重してください。

報告書のマスキングによって元ログへの追跡可能性を失わないようにしてください。

元ログそのものは変更しないこと。

## 9. 集計の正確性と完全性

以下を保証できる設計にしてください。

- 同一リクエストの重複計上を防止する。
- 複数ルールに一致したリクエストを正しく扱う。
- 複数エンジンに一致したリクエストを正しく扱う。
- 事案数とリクエスト数を区別する。
- 検出数と不審リクエスト数を区別する。
- パース不能行を隠蔽しない。
- 除外されたログと除外理由を識別できる。
- 各種解析上限による影響を識別できる。
- 欠損値とゼロを区別する。
- 未対応と検出なしを区別する。
- 正確な件数と下限値・推定値を区別する。
- 部分解析時に完全な調査結果であるかのように表示しない。
- HTML、JSON、CSV 間で集計値が矛盾しない。
- 丸め誤差以外の割合の不整合が発生しない。

全体集計と調査観点別集計の関係を文書化してください。

## 11. 開発方法

t_wada の TDD に則り、Red → Green → Refactoring のサイクルを短く回し、細粒度でコミットしてください。

- まず期待する振る舞いをテストで表現する。
- テストの失敗を確認する。
- テストを通すための最小限の実装を行う。
- テスト成功後にリファクタリングする。
- 既存のテストを維持する。
- テストの容易性を理由にプロダクションコードの設計を不必要に複雑化しない。
- 既存機能を破壊しない。
- 不必要な依存ライブラリを追加しない。

各フェーズについて以下を実施してください。

1. 最新の main ブランチを基点とする専用 Git worktree を作成する。
2. フェーズの目的に沿って実装する。
3. TDD による細粒度コミットを行う。
4. テスト、静的解析、必要な性能測定を実施する。
5. セルフレビューを実施する。
6. 妥当なレビュー指摘を修正する。
7. Pull Request を作成する。
8. CI の成功およびマージ条件の充足を確認する。
9. Pull Request をマージする。
10. 元のリポジトリを最新化する。
11. 使用した worktree を削除する。
12. 次のフェーズへ進む。

未コミットの利用者変更を上書き・削除しないでください。

CI 失敗や権限不足などによってマージできない場合は、問題を隠蔽したり保護設定を迂回したりせず、実施状況と阻害要因を報告してください。

## 12. 必須テスト観点

少なくとも以下を検証してください。

- 正常アクセスのみのログ
- 不審アクセスのみのログ
- 正常アクセスと不審アクセスが混在するログ
- 同一リクエストが複数ルールに一致するケース
- 複数エンジンが同一リクエストを検出するケース
- 同一内容の異なるリクエスト
- 複数ログファイルにまたがる事案
- ローテーション済みログ
- gzip ログ
- 時系列順序が前後するログ
- パース不能行を含むログ
- 空のログ
- 必要項目が欠損したログ
- GeoIP DB が存在しない場合
- GeoIP DB が利用可能な場合
- 解析上限に達した場合
- 入力ファイルを読み込めない場合
- 全件出力時に入力ファイルが変更された場合
- 解析終了時に成立する統計的検出
- 攻撃成否が不明なケース
- HTTP 200 だが攻撃成功を確認できないケース
- HTTP 403・404 だが攻撃失敗を断定できないケース
- HTML / CSV インジェクションを意図した文字列
- 大規模ログでの資源使用量
- HTML、JSON、CSV の集計値の整合性
- 日本語・英語のレポート生成
- 既存 CLI と出力形式の後方互換性

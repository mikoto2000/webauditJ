# 幹部・技術者向けレポートと二次調査の引き継ぎ

`--report-dir` は、アクセスログの既存分析から2種類のHTMLと二次調査の計画・依頼文を同時出力します。追加ログ、LLM、APIキー、Node.js、ネット接続は通常利用に不要です。

```powershell
java -jar target/webauditJ.jar access.log --report-dir investigation --lang ja
```

`investigation/index.html` を開き、「まず、結果と次の対応を見る」を選びます。

最初の3項目だけで「何が見つかった？」「被害は出ている？」「次に何をする？」を確認できます。「何が見つかった？」には、02に掲載しているリスクを種類ごとにまとめた一覧があり、各項目から根拠へ進めます。02の表は、リスク・成否判定結果・優先度・影響・条件・理由・次の確認・対象の種類・関連事案IDを、それぞれ独立した列で表示します。具体的な対応はその下のリンクから、証拠やログの詳細は技術者向け報告から確認してください。「成功の疑い」は被害の確定ではなく、「成否不明」は証拠が足りず判断できない状態です。

| ファイル | 用途 |
|---|---|
| `executive-summary.html` | 推奨対応レベル、条件付き潜在リスク、選択肢とトレードオフ、承認事項、アクション、引上げ・終了条件、判断限界 |
| `technical-report.html` | 既存の詳細分析・カバレッジ・統計・証拠と、リスク解釈の根拠・二次調査プロンプト生成 |
| `executive.html` / `technical.html` | それぞれの別名 |
| `report.json` | 既存分析と共通の `decision_support` / `secondary_investigation` モデル |
| `data/` | 分析要約、事案・独立検出、リスク、対応、構造化二次調査計画 |
| `evidence/source-references.json` | 事案ID・独立検出IDから元ファイル・行・証拠IDへの参照。代表証拠は既存の保持上限に従う |
| `suspicious-requests.csv` / `related-requests.csv` | 不審アクセス・関連アクセスの1行ごとの一覧。分類をA列、日時をB列とし、アクセス情報の後にID類をまとめて配置 |
| `risk-register.csv` / `action-plan.csv` | リスクと推奨アクション。時期・担当候補は提案で、実際の期限・割当ではない |
| `prompts/secondary-investigation-all.md` | 全事案と独立検出の依頼文 |
| `prompts/secondary-investigation-priority.md` | 高優先度の事案のみ。該当なしなら依頼開始文を生成せず、その旨を表示 |
| `prompts/cases/<ID>.md` | 個別対象の依頼文。WebAudit本来の事案ID・検出IDを維持 |
| `report-spec.md` / `templates/` | 二次・三次調査にも引き継ぐ共通レポート仕様とHTMLテンプレート/CSS |
| `risk-rules.json` | 版管理された対応レベル・優先度・条件付きリスクの定義 |
| `README.md` / `manifest.json` | 閲覧・再現方法、入力/成果物ハッシュ、ルールと仕様版、完全性 |

既存JSONスキーマへの追加フィールドです。HTMLは幹部向け・技術者向けの2種類に統一し、一式の従来の `report.html` は生成しません。`-o report.html` / `--format html` も同じ技術者向け報告を使い、スクリプトとリンク先資料をHTMLに埋め込みます。JSON/CSV、watchの出力とルート直下CSVは維持します。

03では、推奨対応に応じて責任者が行う手順を表示します。調査が必要な場合は担当者の選定、記録の保全、調査対象・範囲の決定、初回報告期限の設定を案内します。判断保留の場合は入力の確認と再解析、候補がない場合は記録・監視の担当と次回確認日の設定を案内します。03は調査全体の方針、02は確認する対象、04は対象ごとの実施計画という関係です。04の表は、対象・対応内容・完了条件・時期目安・担当候補・必要資料の順に、それぞれ独立した列で表示します。対象の事案IDは左端に配置します。個別の制限や停止は対象の証拠と業務影響で判断します。別の方針を検討するときに使う比較表は折りたたんでいます。

付録Dの調査方法では、検出理由の適用性、アクセスの関連付け、不足する記録と解析上限の3点を先に確認します。解析の仕組み・実効設定・全ルールは折りたたんでいます。全ルールは検出条件の一覧であり、今回検出された事案の証拠は第4章で確認します。

判定の定義は末尾の「付録A 判定の読み方」にまとめています。技術者向け本文は第1〜6章で構成し、第3章のリスク対応一覧と第4章の詳細分析から付録へ進めます。件数や優先対象を再掲する総合評価の章は設けず、必要な注意事項を第1章と第4章に残しています。重複する事案一覧の章は設けず、第4章の詳細とCSVで優先対象以外も確認できます。独立した制約・限界の章は設けず、実行時の制約と診断は第2章、事案固有の未確認事項は第4章、一般的な限界・表示上限・マスキングや共有時の注意は付録Cに整理しています。調査方法は付録D、アクセスログ全体の統計は付録Eへ移し、第3章から必要時に参照できます。既存の内部アンカーは維持しています。

技術者向けの第3章は、「不正アクセス疑いがあった観点」として幹部向け02の上位10対象を同じ順で示し、リスク・調査観点や検出項目・根拠の詳細を対応付けます。WebAudit事案は事案ID、独立エンジンはエンジンとルールIDで対応付け、名前だけで関連付けません。対応する行が表示範囲になければ、その旨を示します。続いて、同じ対象の未確認情報・確認する記録・次の確認を、別ツールや別作業に引き継ぐ事項として示します。一般的な未対応・未実施・検出なしの項目や全観点・全ルールの評価状況は「付録B」にまとめ、件数・評価状態・検出有無を別々の列で示します。CSVとJSONの件数や評価は変更しません。リスクとの対応関係、評価行が表示範囲にない場合の意味、評価状態と検出有無の組み合わせの読み方は、付録Aの凡例で確認できます。

第4章の事案詳細は、先頭に「何があったか」「何を疑うか」「何が未確認か」「次に何を確認するか」を表示します。WebAudit事案には含まれるアクセス記録数と最大3件の代表記録を示します。長い要求先は要約で省略し、完全な値は詳細とCSVに保持します。独立エンジンの検出では直接検出・関連記録の件数を分け、被害確定や同一主体を推定しません。元ログ・ルール・統計・判定理由は折りたたんでいます。「次に何を確認するか」からは、事案ID・検出IDで対応付けた第5章の調査アクションへ直接進めます。引き継ぎ欄からも対象の要点へ進めます。

## アクセスログの一覧を開く

成果物一覧、幹部向け報告、技術者向け報告の冒頭にある「不審アクセスのログ一覧を開く（CSV）」から開けます。CSVはA列が `attack_categories`（検出された不正アクセスの分類）、B列が `timestamp`（日時）、C列から接続元IPなどのアクセス情報です。分類は不正の確定を意味しません。

リクエスト・事案・検出・ルール・入力ファイル・直接検出・関連検出のIDは末尾7列にまとめています。列名・値は維持していますが、以前のCSVとは列順が変わるため、プログラムで読む場合は列名で参照してください。関連アクセスCSVも同じ列順です。

## 作業の依頼と結果報告（第6章）

第4章の事案詳細と第5章の調査アクションにある「この対象の調査を依頼する」から、第6章の依頼文生成へ進めます。対象IDを引き継ぎ、その1対象だけを選択します。対象指定のリンクで再読込みした場合も同じ対象を選びます。不明な対象指定は選択を空にし、別対象の依頼を生成しません。

第3章の優先一覧とは別に、第6章では全保持対象を選択でき、第3章に未掲載の対象も区別して表示します。未評価は優先順位未設定を意味し、低優先度・検出なしではありません。選択件数と対象IDを生成画面の冒頭に表示します。

調査後は、対象IDと範囲、結論と評価変更、支持・反証、被害と影響範囲、実施作業と確認結果、未解決事項と次の判断をまとめて責任者へ報告します。一次成果物を残し、追加結果は別成果物に保存します。進捗管理や結果の自動取込みは行いません。対応強化・終了条件は幹部向け05へリンクしています。

第5章の表は、対象ID・優先度・種別・対応内容・確認する記録・確認方法・成功の判断材料・失敗の判断材料・調査依頼を独立した列にしています。対応理由・期間・IP・ホスト・要求先は補足表へ分けています。

## 二次調査プロンプトの使い方

技術者向け報告の上部にある「二次調査プロンプト生成」を選びます。事案別の引き継ぎ欄から、その対象だけを選ぶこともできます。

1. 全事案・独立検出、高優先度のみ、または個別チェックで調査対象を選びます。
2. 「一次調査レポートのフォルダー」には今回の成果物一式、「追加ログ・資料のフォルダー」には承認を得て収集した資料、「二次調査結果の保存先」には別の出力先を指定します。
3. コピーまたはMarkdown保存で依頼文を取り出します。ローカルHTMLではクリップボードが利用できない場合があり、その場合は選択された本文をCtrl+C / Command+Cでコピーできます。
4. 資料にアクセスできる調査エージェントへ依頼します。このUIはファイルを読まず、外部送信・LLM呼出し・資料収集・調査の実行や承認を行いません。

パスは依頼先の作業ディレクトリ基準です。画面は実在性や権限を確認せず、単純な出力先重複と制御文字を拒否するだけです。実行側は実パス、シンボリックリンク、既存成果物を再確認し、入力の変更・上書きを避けます。

## 追加調査後の判断（05）

05は04の追加調査結果を受け取ってから使います。共通の判断ルールと調査を見送る場合の注意は1回だけ表示します。機密資源、認証・認可、意図しない処理、権限外データ取得、可用性の各プロファイルには、追加証拠を得た場合の固有の判断条件を設定しています。探索などの一般確認では共通条件を使います。検出やHTTPステータスだけで被害を確定したり、自動で制限・停止したりしません。

同じ条件が当てはまる対象はまとめて表示し、02の対象へリンクします。幹部向けの表示上限は引き続き上位10対象で、全対象の条件はJSONと `risk-register.csv` に保持します。共通条件は `decision_support.common_escalation_condition` / `common_if_deferred`、個別対象の条件は既存の `escalation_condition` / `if_deferred` に出力します。ルール版は `webaudit/response-rules-2` です。

## リスク解釈と判断の範囲

既存検出結果を変更せず、検出と別の解釈層で条件付きシナリオを作ります。機密資源、認証、注入等の処理、応答量、可用性、一般確認の順で該当プロファイルを選びます。すべてのプロファイルと適用順、対応基準は `risk-rules.json` に記録します。

- 成功の疑い、または既存のcritical/high事案は高優先度、mediumは中、それ以外は低。これは既存の追加調査基準であり、攻撃確率や組織固有の重大度ではありません。
- Hub/Aura等の独立検出は別の調査対象として保持し、優先度・成否を未評価にします。事案と統合したり、候補の件数を一意な攻撃数として合算しません。
- 高優先度/成功の疑いがあれば「優先的な追加調査」。その根拠がなく、解析成功0件または部分解析なら「判断保留」。それ以外に候補があれば「計画的な追加調査」、候補なしなら「監視継続」です。
- 「緊急対応」は追加証拠を確認した責任者の判断条件として提示し、アクセスログだけで自動適用しません。終了・リスク受容・被害額・最新状態・実期限を自動確定しません。
- HTTPステータスだけでは侵害・認証・内部処理の成否を確定しません。攻撃確度は引き続き既存モデルの未評価を維持し、スコアから確率を捏造しません。

全レポートは同じ共通モデルを参照し、既存の入力・件数・証拠・出力容量上限を引き継ぎます。統計・カバレッジは今回の範囲と設定で評価したもので、未検出や監視継続は安全の証明ではありません。

## 共通レポート生成仕様の引き継ぎ

プロンプトは、まず `report-spec.md` と `templates/` を読むことを要求します。幹部向け・技術者向けの具体的構成、同一データとID、支持/反証と評価変更、図表、A4印刷/PDF、オフライン、安全表示、機密値マスク、出力ディレクトリ構成、表示・リンク・検索・印刷・整合性の完了確認を指定します。

テンプレートは本体が使うHTML/templateソースであり、ログをテンプレートとして解釈するものではありません。二次調査ではデータ構造と必要な章に合わせて安全なレンダラーで適用します。テンプレートを生成しただけで、二次調査や表示検証が完了したことにはなりません。

## 安全性・再現性

ログ由来のIP、経路、UA、時刻等は `untrusted_observations` に隔離します。依頼文の作業指示には、本体所有のガイダンス、生成ID、件数と品質だけを使い、ログ・調査タイトルを直接埋め込みません。依頼先でも原本・JSON・CSVの値を指示として実行しない必要があり、分離だけでプロンプトインジェクションを完全に防ぐ保証はありません。

既存のマスク・制御文字の可視化後に計画を作り、HTMLはcontext-aware escape、スクリプトデータはJSONのHTMLエスケープ、CSVは数式対策を適用します。`--include-sensitive-evidence` は既存と同じ明示的解除です。一般的秘密パターンのマスクは、任意の個人情報・秘密の完全検出を保証しません。

LLMは依頼先で実行し、外部通信・ログ転送・パッケージ導入・実システム接続や変更をしない制約を引き継ぎます。原本、設定、ルール版とハッシュが同じなら判断・調査計画・既定プロンプトは再現できます。レポートの実行日時、ビルド情報、原本のパスによるIDは環境により変わります。

ブラウザーの操作ロジックとGo出力の一致は、Nodeが存在するとき `TestBundleAudienceBrowserPromptParity` がDOMスタブで検証します。Nodeは本体の実行依存ではありません。実ブラウザー・印刷・大規模実測は別の検証として記録してください。

幹部向け本文のリスク/アクション表は、成功の疑い→高→中→低→未評価の順で上位10対象に制限します。全保持対象は共通モデル・技術者向け・CSV・個別プロンプトに残り、表示省略と解析の不完全性を区別します。
